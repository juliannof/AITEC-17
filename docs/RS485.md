# RS485 — Protocolo de Comunicación Serial (iMakie)

Documentación exhaustiva del bus RS485 que conecta master (P4/S3) con slaves (S2). Incluye protocolo binario, timing, máquina de estados, paquetes, CRC, troubleshooting.

**Responsable:** iMakie Development Team  
**Última actualización:** 2026-07-22  
**Estado:** En producción (2 buses activos: A=P4, B=S3)

---

## ⚠️ ACTUALIZACIÓN DE ARQUITECTURA (2026-07-22) — S2 dueño de calibración, S3 transparente

**El S2 es ahora dueño único de la calibración y del mapeo PitchBend↔ADC.** El S3 (y el P4, cuando se porte) ya no guardan rango calibrado por canal, no orquestan cascada de calibración, y no recalculan nada — solo transportan `faderTarget`/`faderPos` como **PitchBend crudo 0-16383** de punta a punta.

Esto invalida partes significativas de las secciones §2 (protocolo), §4 (calibración) y §5 (control en tiempo real) de este documento tal como estaban escritas para el modelo anterior (S3 mapeaba ADC↔PB y orquestaba una cascada de calibración por todos los slaves). Se han dejado esas secciones **como contexto histórico** — documentan decisiones válidas en su momento — pero marcadas explícitamente como obsoletas donde aplica. Ver el resumen correcto abajo.

**Modelo actual (resumen):**
- `MasterPacket.faderTarget` / `SlavePacket.faderPos`: PitchBend 0-16383, sin mapeo intermedio en S3/P4.
- Calibración: el S2 se autocalibra en su propio boot (diferido hasta tener lecturas ADC reales — ver `FADER.md`). El S3 solo puede pedir una recalibración puntual vía `FLAG_CALIB` (`setCalibrate()`), y lee pasivamente `SLAVE_FLAG_CALIB_DONE`/`SLAVE_FLAG_CALIB_ERROR` para marcar el canal operativo/degradado en `ChannelData.calibrated` — sin cascada, sin reintentos, sin captura de rango.
- Campos de `ChannelData` (S3) **eliminados**: `calibrating`, `calibRetries`, `stableRespCount`, `lastRawPitchBend`, `calibratedMin`, `calibratedMax`, `_filteredFaderPos[]`. Se conserva `calibrated` (uso informativo).
- P4 queda **incompatible** con este firmware de S2 hasta que se porte la misma Fase 6 (ver CHANGELOG sesión 2026-07-22).

Detalle completo de la migración: ver **CHANGELOG.md**, sesión 2026-07-22.

## 1. TOPOLOGÍA Y CONFIGURACIÓN

### 1.1 Buses RS485

| Bus | Master | Slaves | TX | RX | EN | Baudrate |
|-----|--------|--------|----|----|-------|----------|
| **A** | P4 (ESP32-P4) | 9× S2 (IDs 1-9) | GPIO50 | GPIO51 | GPIO52 | 500 kbaud |
| **B** | S3 (ESP32-S3) | 8× S2 (IDs 1-8) | GPIO15 | GPIO16 | GPIO1 | 500 kbaud |

**S2 Slave (ambos buses):**
- TX = GPIO8
- RX = GPIO9
- EN = GPIO35

### 1.2 Configuración Física

```cpp
// S2 setup (RS485.cpp)
Serial1.setRxBufferSize(512);      // ⚠️ ANTES de Serial1.begin()
Serial1.begin(500000, SERIAL_8N1, RX_PIN, TX_PIN);
pinMode(EN_PIN, OUTPUT);
digitalWrite(EN_PIN, LOW);         // RX por defecto
```

**Crítico:** `setRxBufferSize()` **ANTES** de `begin()` — buffer por defecto es 64B, insuficiente.

### 1.3 Topología Star

```
        Master (P4 o S3)
            │ RS485 (500kbaud)
            │
     ┌──────┴──────┬──────────┬──────────┐
     │             │          │          │
    S2-1         S2-2        S2-3  ...  S2-9/8
  (trackId=1) (trackId=2) (trackId=3)
```

- **Sin terminadores explícitos** (bus corto, <10m probado estable)
- **Colisión imposible:** Master es autoridad única (nunca slave transmite sin petición)

## 2. PROTOCOLO BINARIO

### 2.1 MasterPacket (Master → Slave)

Enviado cada ~20ms a cada slave en ciclo round-robin.

**⚠️ `fader_target` actualizado (2026-07-22):** ya NO es rango ADC mapeado por el master — es **PitchBend crudo de Logic, 0-16383**. El S2 mapea a su propio rango ADC calibrado. Ver actualización al inicio de este documento.

```cpp
struct MasterPacket {
    uint8_t  start_byte;           // 0xAA
    uint8_t  slave_id;             // 1-9 (P4) o 1-8 (S3)
    uint8_t  track_name[8];        // ASCII track name (ej: "Track 1")
    uint16_t fader_target;         // PitchBend crudo de Logic, 0-16383 (2026-07-22 — antes: ADC 0-27000)
    uint8_t  vu_level;             // 0-127 (feedback a esclavo para display)
    uint8_t  flags;                // bit0=FLAG_CALIB, bit1=..., etc.
    uint8_t  crc8;                 // Checksum
    // Total: 16 bytes
};
```

**Flags (bits):**
- `bit 0` = FLAG_CALIB (ordena calibración a S2)
- `bit 1` = FLAG_TOUCH_EN (habilita sensor táctil)
- `bit 2` = FLAG_MOTOR_DIS (deshabilita motor)

### 2.2 SlavePacket (Slave → Master)

Enviado inmediatamente tras recibir MasterPacket (latencia crítica <150µs).

**⚠️ `fader_pos` actualizado (2026-07-22):** ya NO es ADC crudo — es **PitchBend 0-16383**, mapeado y filtrado (EMA) por el propio S2 con su rango calibrado. `SLAVE_FLAG_CALIB_SENDING`/`CALIB_IS_MIN` quedaron OBSOLETOS (bits no reciclados, nunca se envían) — el S2 ya no manda min/max por el bus, los gestiona internamente.

```cpp
struct SlavePacket {
    uint8_t  start_byte;           // 0xBB
    uint8_t  slave_id;             // Echo del ID recibido
    uint16_t fader_pos;            // PitchBend 0-16383, ya mapeado por el S2 (2026-07-22 — antes: ADC 0-27000)
    uint8_t  buttons;              // bits 0-3: REC/SOLO/MUTE/SELECT
    uint8_t  encoder_delta;        // -127..+127 (encoder movimiento)
    uint8_t  encoder_button;       // bool (encoder push)
    uint8_t  flags;                // bit0=CALIB_DONE, bit1=CALIB_ERROR, bit2/3=OBSOLETO
    uint8_t  crc8;                 // Checksum
    // Total: 9 bytes
};
```

**Flags Slave (bits):**
- `bit 0` = SLAVE_FLAG_CALIB_DONE (calibración completada — lectura pasiva en S3, sin cascada)
- `bit 1` = SLAVE_FLAG_CALIB_ERROR (calibración fallida)
- `bit 2` = SLAVE_FLAG_CALIB_SENDING — **OBSOLETO 2026-07-22**, rango ADC es interno del S2
- `bit 3` = SLAVE_FLAG_CALIB_IS_MIN — **OBSOLETO 2026-07-22**, ídem

### 2.3 CRC8 Calculation

```cpp
uint8_t crc8(uint8_t *data, uint8_t len) {
    uint8_t crc = 0xFF;
    for (int i = 0; i < len; i++) {
        crc ^= data[i];
        for (int j = 0; j < 8; j++) {
            if (crc & 0x80) {
                crc = (crc << 1) ^ 0x07;  // Polinomio STM32 0x07
            } else {
                crc = crc << 1;
            }
            crc &= 0xFF;
        }
    }
    return crc;
}
```

## 3. TIMING CRÍTICO

### 3.1 Ciclo de Comunicación (20ms)

```
T=0ms:     Master envía MasterPacket a S2-1
T≈100µs:   S2-1 recibe, procesa
T≈150µs:   S2-1 envía SlavePacket
T≈300µs:   Master recibe respuesta
T=300µs:   GAP (espera antes de siguiente esclavo)
T=600µs:   Master envía MasterPacket a S2-2
...
T=20ms:    Ciclo completo, reinicia con S2-1
```

### 3.2 Máquina de Estados (Master)

```
IDLE (espera GPIO o timeout)
  ↓
SEND_MASTER (TX_EN=HIGH, enviar MasterPacket)
  ↓
TX_DONE (esperar fin transmisión)
  ↓
WAIT_RESP (RX_EN=HIGH, esperar SlavePacket)
  ├─ Si llega SlavePacket válido:
  │   ↓ RS485Handler::_handleResponse()
  │   ↓ Procesa fader_pos, botones, encoder, flags calib
  │   ↓ DONE
  │
  └─ Si timeout (3000µs):
      ↓ Reintenta FLAG_CALIB (hasta 3 veces)
      ↓ Marca slave NOT_CALIBRATED
      ↓ DONE

GAP (delay 300µs)
  ↓ vTaskDelay(1) para yield (S2 single-core)
  ↓
NEXT_SLAVE (siguiente ID)
  ↓ Vuelve a IDLE
```

### 3.3 Timings en config.h

```cpp
// RS485 timing (Master y Slave)
#define RS485_TX_EN_SETUP_US      30    // µs pre-transmisión
#define RS485_TX_DONE_SETUP_US    30    // µs post-transmisión
#define RS485_RESP_TIMEOUT_US   3000    // µs espera respuesta
#define RS485_GAP_US             300    // µs entre slaves
#define RS485_POLL_CYCLE_MS       20    // ms ciclo completo
#define RS485_BAUD           500000     // 500 kbaud
```

## 4. CALIBRACIÓN VÍA RS485 (2026-05-16 19:25) — ⚠️ OBSOLETO 2026-07-22, ver nota arriba

**Toda esta sección (§4) describe el modelo ANTERIOR, donde el S3 orquestaba una cascada de calibración de todos los slaves y capturaba `calibratedMin`/`calibratedMax` por canal.** Ese modelo ya no existe: el S2 se autocalibra solo en su propio boot, y el S3 solo puede pedir una recalibración puntual (`FLAG_CALIB` vía `setCalibrate()`) y leer pasivamente `CALIB_DONE`/`CALIB_ERROR`, sin cascada, sin reintentos, sin captura de rango. `_triggerNextCalibration()`, la detección de reinicio por cascada (§4.4) y el skip+cascade de timeout (§4.5) fueron eliminados del código.

Se conserva el contenido original abajo como **contexto histórico** (documenta un diseño real que funcionó en su momento y las lecciones de esa etapa siguen siendo válidas conceptualmente — p. ej. "los topes mecánicos se detectan por stall, nunca por umbral absoluto"), pero **no describe el comportamiento actual del sistema**. Ver CHANGELOG.md sesión 2026-07-22 para el detalle de la migración, y `FADER.md` para cómo calibra el S2 ahora.

### 4.1 Arquitectura Calibración

**Iniciador:** Master (S3 o P4) ordena calibración al boot, **independiente de Logic conectado**.

**Propósito:** Mapear ADC físico S2 (0-27000) para que Logic pueda controlar faders 0-16383.

**Criticidad:** S3 ordena secuencial (un slave a la vez) para evitar colisiones RS485.

### 4.2 Flujo Calibración S2

```
Master envía MasterPacket[FLAG_CALIB]
     │ (pkt.connected puede ser 0 o 1)
     ↓
S2 RS485Handler::onMasterData()
     ├─ ANTES de procesar desconexión (2026-05-16 19:24):
     │  Motor::requestCalibration()
     │     ├─ Si fader EN 0: startCalib() inmediato
     │     └─ Si fader ≠ 0: goToMin() → baja a 0 → luego startCalib()
     │
     ├─ Procesa pkt.connected (CONNECTED/DISCONNECTED)
     │  (Motor ya está en GOING_TO_MIN, no bloqueado)
     │
Motor::update() máquina de estados:
     ├─ GOING_TO_MIN: cuando llega a 0 → WAITING_FOR_CALIB
     ├─ WAITING_FOR_CALIB: inicia startCalib() → CALIBRATING
     └─ CALIBRATING: (3-5s) busca min/max, settles, DONE
     
Calibración completada:
     ├─ buildResponse() envía SlavePacket[CALIB_DONE, CALIB_SENDING, CALIB_IS_MIN]
     │  (faderPos = ADC_MIN)
     ├─ buildResponse() envía SlavePacket[CALIB_DONE, CALIB_SENDING]
     │  (faderPos = ADC_MAX)
     └─ buildResponse() envía SlavePacket[CALIB_DONE]
        (operación normal, faderPos = posición actual)
```

### 4.3 Flujo Calibración S3 — Cascada automática (2026-05-22)

```
S3 boot → RS485 task activo inmediatamente
     │
     └─ _handleResponse() cuenta respuestas estables de Slave 1
         (SLAVE_CALIB_SETTLE_RESPONSES = 5 respuestas × 10ms = ~50ms grace)
         │
         └─ Cuando Slave 1 alcanza 5 respuestas:
              calibrate=true → FLAG_CALIB enviado en siguiente ciclo
              │
RS485Master::_handleResponse() recibe CALIB_DONE de Slave 1:
     ├─ calibrated[1] = true
     ├─ Cascada: calibrate[2] = true → FLAG_CALIB a Slave 2
     │
     └─ Cuando Slave 2 CALIB_DONE:
          calibrated[2] = true
          Cascada: calibrate[3] = true → ...
          │
          └─ Cuando Slave N CALIB_DONE:
               log_i("[CALIB] Cascada completa")

Si TIMEOUT > MAX_CALIBRATION_RETRIES (5) durante calibración activa:
     └─ LED rojo + slave marcado defectuoso + cascada continúa (NO HALT — 2026-05-27)

Si Slave reporta CALIB_ERROR:
     ├─ calibRetries++ → stableRespCount=0 (grace period de nuevo)
     └─ Si calibRetries >= MAX_CALIBRATION_RETRIES → LED rojo + skip + cascada continúa
```

**Constantes clave (config.h S3):**
```cpp
#define MAX_CALIBRATION_RETRIES      5   // timeouts RS485 o errores CALIB_ERROR antes de marcar defectuoso
#define SLAVE_CALIB_SETTLE_RESPONSES 5   // respuestas estables antes de primer FLAG_CALIB
#define POLL_CYCLE_MS               10   // grace period = 5 × 10ms = ~50ms
```

**Puntos críticos:**
- **Grace period de 50ms** antes de disparar calibración — esclavo termina su `setup()` primero
- **Solo Slave 1 arranca automáticamente** — slaves 2..N solo se calibran por cascada
- **Cascada event-driven**: Slave N+1 arranca exactamente cuando Slave N reporta `CALIB_DONE`
- S2 envía **2 paquetes de MIN/MAX**, Master captura con `CALIB_SENDING` flag
- **FLAG_CALIB procesado ANTES de desconexión** en S2 (Motor puede estar activo)
- **Calibración independiente de Logic** — ocurre al boot, antes de handshake

**Logs esperados en monitor serie (boot normal):**
```
[CALIB] Slave 1 estabilizando 1/5
[CALIB] Slave 1 estabilizando 2/5
...
[CALIB] Slave 1 estable (5 resp) — arrancando cascada de calibración
[CALIB] Slave 1 ✓ CALIBRADO OK: MIN=44 MAX=26448
[CALIB] Cascada → Slave 2
[CALIB] Slave 2 ✓ CALIBRADO OK: MIN=XX MAX=XXXXX
[CALIB] Cascada completa — todos los slaves calibrados
```

### 4.4 Detección de Reinicio de Slave (2026-05-27)

**Problema resuelto:** Si un S2 se reinicia durante operación normal, S3 lo tenía marcado como `calibrated=true` y nunca volvía a calibrarlo. El slave quedaba sin ADC min/max válidos.

**Señal de protocolo utilizada:** Tras calibración exitosa, `Motor::getCalibState()` devuelve `DONE` permanentemente. `buildResponse()` en S2 incluye `SLAVE_FLAG_CALIB_DONE` en **cada** paquete normal post-calibración. Tras un reinicio, el estado vuelve a `IDLE` y ese flag desaparece — esto es la señal de reinicio.

**Lógica en `RS485Master::_handleResponse()` (RS485.cpp S3):**

```cpp
// bloque else (ni calibDone ni calibError)
if (_ch[_currentId].calibrated && !_ch[_currentId].calibrating) {
    // Slave fue calibrado pero ya no reporta CALIB_DONE → reinicio detectado
    _ch[_currentId].calibrated      = false;
    _ch[_currentId].calibRetries    = 0;
    _ch[_currentId].stableRespCount = 0;
    _ch[_currentId].calibrate       = true;
    _ch[_currentId].calibrating     = true;
    _ch[_currentId].dirty           = true;
    log_w("[CALIB] Slave %d: reinicio detectado — recalibrando automáticamente", _currentId);
}
```

**Guards que previenen falsos disparos:**
- `_ch[id].calibrated == true` — solo actúa sobre slaves que YA estaban calibrados; en boot inicial `calibrated=false` y no dispara
- `!_ch[id].calibrating` — no dispara durante la fase `CALIB_SENDING` (que también llega al bloque `else`) porque durante esa fase `calibrating=true`
- Inline (sin llamar `setCalibrate()`) — evita deadlock por el mutex ya tomado en `_handleResponse()`

**⚠️ Interacción con HALT (bug resuelto 2026-05-27):**
La reboot detection pone `calibrating=true` inmediatamente. Si S2 tarda en arrancar tras el reflash (sin RS485 aún), S3 acumulaba 5 timeouts consecutivos con `calibrating=true` → HALT de Core 1. Logic seguía conectando (Core 0 vivo) pero S2s quedaban muertos. Fix: el HALT fue eliminado — ahora usa skip+cascade igual que el path de `CALIB_ERROR`. Ver §4.5.

**Flujo tras detección:**
```
S2 se reinicia (durante operación)
     ↓
S3 obtiene timeouts mientras S2 arranca (~1-5s)
     ↓
S2 vuelve al bus — envía SlavePacket con CALIB_DONE=0 (CalibState::IDLE)
     ↓
S3 _handleResponse(): calibrated=true pero CALIB_DONE=0
     → reinicio detectado
     → calibrate=true, calibrating=true
     ↓
Siguiente MasterPacket incluye FLAG_CALIB
     ↓
S2 Motor::requestCalibration() → calibración normal
     ↓
Cascada continúa si hay slaves posteriores sin calibrar
```

**Log esperado tras reinicio de slave:**
```
[RS485] TIMEOUT slave 3 (#1 consecuciones)
[RS485] TIMEOUT slave 3 (#2 consecuciones)
...
[CALIB] Slave 3: reinicio detectado — recalibrando automáticamente
[CALIB] Slave 3 ✓ CALIBRADO OK: MIN=44 MAX=26490
```

### 4.5 Timeout durante calibración — Skip+Cascade (2026-05-27)

**Comportamiento anterior (hasta 2026-05-27):** Si `_consecutiveTimeouts > MAX_CALIBRATION_RETRIES` con `calibrating=true` → `while(1)` — Core 1 (RS485 task) HALT. Core 0 (MIDI) seguía vivo → Logic conectaba, transport LEDs funcionaban, S2s muertos.

**Comportamiento actual:** Skip + cascade, igual que el path de `CALIB_ERROR`.

```cpp
// RS485.cpp S3 — WAIT_RESP timeout handler
if (!_ch[_currentId].calibrated && _ch[_currentId].calibrating
    && _consecutiveTimeouts > MAX_CALIBRATION_RETRIES) {

    pixels.setPixelColor(0, pixels.Color(255, 0, 0));  // Rojo: señal visual
    pixels.show();
    _ch[_currentId].calibrating  = false;
    _ch[_currentId].calibRetries = MAX_CALIBRATION_RETRIES;  // marcado defectuoso
    log_e("[CALIB] ✗ TIMEOUT Slave %d — marcado defectuoso, continuando cascada", id);

    _triggerNextCalibration(_currentId);  // cascade con wraparound
    _consecutiveTimeouts = 0;
    _busState   = BusState::GAP;
    _stateTimer = micros();
}
```

**Síntoma visible:** NeoPixel S3 ROJO. Sistema continúa — slaves restantes siguen calibrando.

**Log esperado:**
```
[CALIB] ✗ TIMEOUT Slave X — marcado defectuoso, continuando cascada
```

**Causa raíz del bug anterior:** reflash S2 provoca ~2-5s de silencio RS485 (bootloader + setup). Si reboot detection había activado `calibrating=true` (§4.4), los timeouts de esa ventana disparaban el HALT.

## 5. CONTROL DE FADER EN TIEMPO REAL

**⚠️ Actualizado 2026-07-22 — el master (S3/P4) ya NO mapea PitchBend↔ADC.** Solo transporta el valor crudo de Logic; el mapeo con el rango calibrado ocurre en el S2.

```
Logic Pro (usuario mueve fader)
     │ PitchBend 0-16383
     ↓
Master MidiProcessor::processPitchBend()
     │ Passthrough — sin mapeo, sin calibración local
     ↓
Master MasterPacket.faderTarget = PitchBend crudo (0-16383)
     │ cada 20ms
     ↓
Slave recibe faderTarget (PitchBend)
     │ RS485Handler::_pbToADC() mapea con el rango calibrado propio
     ↓
Motor::setTargetForced()/setTargetFromS3() según AutoMode
     │ Calcula error vs posición actual
     ↓
Motor hacia arriba o abajo (dead zone, ver FADER.md)
     │
FaderADC realimenta posición
     │
Slave mapea ADC→PitchBend con su rango calibrado, envía SlavePacket.faderPos (PitchBend)
     │ cada 20ms
     ↓
Master hace passthrough de faderPos — sin remapeo
     ↓
Logic recibe PitchBend, actualiza gráfico
```

**Latencia end-to-end:** <100ms típicamente (3 ciclos RS485 = 60ms)

### 5.1 Routing del faderTarget según AutoMode (2026-05-30)

`RS485Handler::onMasterData()` ya no llama directamente a `Motor::setTargetFromS3()`. En su lugar enruta a través de **`Internal::_applyFaderTarget(mode, target)`**, que decide qué API del motor llamar según el AutoMode (bits 5-7 de `MasterPacket.flags`):

| AutoMode | Acción |
|----------|--------|
| `AUTO_OFF` / `AUTO_READ` | `Motor::setTargetForced()` — DAW absoluto, bypass guard usuario |
| `AUTO_WRITE` | Motor inhibido (no llamada) |
| `AUTO_TOUCH` / `AUTO_TRIM` | `Motor::setTargetFromS3()` — guard cooperativo |
| `AUTO_LATCH` | `setTargetFromS3()` con freeze: tocar congela posición hasta que Logic envíe target >200 cuentas |

`buildResponse()` reporta `touchState` con debounce **específico del modo** (80ms TOUCH/TRIM, 300ms LATCH, 600ms resto), no con el debounce base del motor.

Documentación completa: **[AUTOMODE.md](AUTOMODE.md)**.

## 6. TROUBLESHOOTING

### 6.1 Síntomas Comunes

| Síntoma | Causa Probable | Verificación |
|---------|----------------|--------------|
| Slave no responde | No recibió MasterPacket o CRC incorrecto | Monitor serial: ¿llega paquete? |
| Timeout 3000µs | Slave muy lento o RS485 físico roto | Osciloscopio: ¿hay pulsos en TX/RX? |
| Botones lentos | RS485 saturado o slave bloqueado | Reducir verbose logging (consume CPU) |
| Fader jitter | Ruido ADC no filtrado | Verificar EMA filter en FADER.md |
| Pérdida datos | Buffer RX insuficiente (64B default) | Usar `setRxBufferSize(512)` ANTES `begin()` |
| S2 pantalla oscura tras reconexión | `checkTimeout()` puso brillo a 0 y `onMasterData()` no lo restauraba | Fix 2026-05-27: `setScreenBrightness(255)` en transición CONNECTED |

## 7. OPTIMIZACIONES HISTÓRICAS

### 7.1 Buffer RX (2026-05-15)

**Antes:** `Serial1.begin()` sin `setRxBufferSize()` → buffer 64B por defecto
- Problema: MasterPacket (16B) + SlavePacket (9B) + overhead = pérdida de datos
- Síntoma: Botones lentos, fader se queda atrás

**Fix:** `Serial1.setRxBufferSize(512)` **ANTES** de `begin()`
- Resultado: Buffer 512B → cero pérdida en ciclo normal

### 7.2 vTaskDelay en GAP (2026-05-15)

**Antes:** Loop tight sin yield
- Problema: S2 single-core, CPU bloqueada, Display laggy

**Fix:** `vTaskDelay(1)` en GAP (300µs)
- Permite que otras tareas (Display, Motor, NeoPixel) ejecuten
- Resultado: Responsividad mejorada sin afectar timing RS485

### 7.3 CRC8 (2026-05-12)

**Polinomio:** 0x07 (STM32 estándar)
- Detecta: bit flips aleatorios, paquetes corruptos
- Falsos positivos: <1% en 500kbaud noise normal
